# 05 · 打包与发布

> 目标读者：**要出一个能发给别人的安装包的人**。
> 从「跑一条命令」到「确认包里没夹带你的令牌」，这一篇全覆盖。

---

## 一、总览

**一条命令，一次出两个包。**

```powershell
cd D:\Tools\frp_0.71.0\cikpier
powershell -ExecutionPolicy Bypass -File tools\package.ps1 -Version 1.0.0
```

产物落在**工作区根的 `release/`**（不是项目目录里）：

```
D:\Tools\frp_0.71.0\release\
├── CikPier-v1.0.0-amd64.zip      给普通 x64 电脑
└── CikPier-v1.0.0-arm64.zip      给 Windows on ARM 电脑
```

每个包里**只有 4 个文件**：

| 文件 | 说明 |
|---|---|
| `CikPier.exe` | 图形界面主程序（前端资源已 `go:embed` 进 exe） |
| `frpc.exe` | frp 官方原版二进制（**和主程序同架构**） |
| `使用说明.md` | 给最终用户的说明书 |
| `LICENSE` | Apache License 2.0 |

> **为什么一次出两个**：详情见 §六。简单说 —— x64 包在 ARM 电脑上
> 能靠模拟跑，但 WebView2 在这个组合下有已知的崩溃 bug。

## 二、前置条件

| 需要 | 检查 | 备注 |
|---|---|---|
| Go 1.25+ | `go version` | |
| Wails CLI | `wails version` | 版本要和 `app/go.mod` 里的 Wails 对上（当前 v2.16.0） |
| `frp-bins/win-amd64/frpc.exe` | 存在即可 | x64 打包要用 |
| `frp-bins/win-arm64/frpc.exe` | 可以不存在 | **缺了脚本会自动从 GitHub 下载** |
| `dist-staging/使用说明.md` | 存在即可 | 脚本会检查，缺了直接报错 |

`frp-bins/` 是整个工作区**唯一的官方二进制存放处**，别在别处另存副本。

```
D:\Tools\frp_0.71.0\frp-bins\
├── win-amd64\    frpc.exe  frps.exe  frpc.toml  frps.toml  LICENSE
├── win-arm64\    同上
└── linux-amd64\  frpc  frps  *.toml  LICENSE
```

## 三、脚本到底做了什么

对**每个架构各跑一遍**下面四步（默认 amd64 先、arm64 后）：

### 第 1 步 · 编译

```powershell
wails build -clean -skipbindings -platform windows/<架构> -o CikPier.exe
```

- `-clean`：先清空 `app/build/bin/`
- `-skipbindings`：不生成 `wailsjs/` 绑定（本项目前端不需要，见 `02-代码地图.md`）
- `-o CikPier.exe`：固定输出名，**避免交叉编译时 Wails 自动加架构后缀**

> ⚠ **编译前脚本会自动杀掉占用 `app/build/bin/` 的进程。**
> 典型情况是上次 `wails dev` 顺手拉起的 `frpc.exe` 还在跑。
> 不清掉的话 `-clean` 会失败，而报错是
> `unlinkat ...: Access is denied.` —— 完全看不出是进程占用。

### 第 2 步 · 收集到 `dist-staging/`

把 `app/build/bin/CikPier.exe` 拷进 `dist-staging/`，然后：

1. **清掉过期的其它 exe** —— 改了名或换了架构后留下的旧主程序
2. **保证 `frpc.exe` 是当前架构的** —— 见下方警告

> ⚠ **这一步是按「架构」判断要不要重拷 `frpc.exe` 的，不是按「文件在不在」。**
>
> 因为连跑两个架构时，处理 arm64 那一步看到的 `dist-staging\frpc.exe`
> 是 **amd64 那一步刚留下的**。如果只看"文件存在"就跳过拷贝，
> 就会把 x64 的 frpc 打进 arm64 的包，最后才在架构校验那里炸掉。
>
> 运行日志里能看出区别：
> ```
> ================ amd64 ================
>       dist-staging 里的 frpc.exe 已是 amd64，沿用
> ================ arm64 ================
>       frpc.exe 来自 D:\...\frp-bins\win-arm64\frpc.exe     ← 主动重拷
> ```

`frpc.exe` 的查找顺序：

| 架构 | 候选（按顺序） |
|---|---|
| amd64 | `-FrpcPath` 指定的 → `frp-bins/win-amd64/frpc.exe` → `packages/frpc-客户端部署包/windows/frpc.exe` |
| arm64 | `-FrpcPath` 指定的 → `frp-bins/win-arm64/frpc.exe` → **自动从 GitHub 下载** |

### 第 3 步 · 自检

1. **必需文件齐全**：`CikPier.exe`、`frpc.exe`、`使用说明.md`
2. **架构校验** —— 读两个 exe 的 PE 头：
   - 主程序的机器码必须等于目标架构
   - `frpc.exe` 的机器码必须和主程序一致
3. **版本号交叉检查** —— 读 `app/about.go` 里的 `appVersion`，
   和 `-Version` 不一致时**打印警告**（不中断）

PE 机器码对照：

| 机器码 | 含义 |
|---|---|
| `0x014C` | x86（32 位） |
| `0x8664` | amd64（x64） |
| `0xAA64` | arm64 |

> ⚠ **架构校验这步不能省。** 主程序和 `frpc.exe` 架构不一致时，
> **程序界面能正常起来，但 frpc 起不来**，现象非常隐蔽 ——
> 用户只会看到"一直在连接"。

### 第 4 步 · 打 zip

```powershell
Compress-Archive -Path dist-staging\* -DestinationPath release\CikPier-v<版本>-<架构>.zip
```

两个架构都带架构后缀。打完之后脚本还会：

- **删掉旧命名产物** `release/CikPier-v<版本>.zip`（早期 amd64 不带后缀的名字），
  免得它和新产物混在一起
- 打印 `release/` 下所有 `CikPier*.zip` 的汇总

## 四、参数详解

| 参数 | 默认 | 说明 |
|---|---|---|
| `-Version 1.0.0` | 空 | 包名里带版本号。**强烈建议每次都传** |
| `-Arch both` | `both` | `both` / `amd64` / `arm64` |
| `-SkipBuild` | 关 | 只重打包，不重新编译 |
| `-RefreshFrpc` | 关 | 强制重新拷一份 `frpc.exe` 进包 |
| `-FrpcPath <路径>` | 空 | 手动指定 `frpc.exe` 位置 |
| `-FrpVersion 0.71.0` | `0.71.0` | 本地没有 arm64 版 frpc 时从 GitHub 下哪个版本 |

### ⚠ `-SkipBuild` 和 `-FrpcPath` 的约束

这两个开关**只能配合单一架构**：

```powershell
# ✅ 可以
-SkipBuild -Arch arm64
-FrpcPath D:\somewhere\frpc.exe -Arch amd64

# ❌ 直接报错
-SkipBuild                    # 默认 -Arch both
-FrpcPath C:\x\frpc.exe       # 默认 -Arch both
```

**为什么**：

- `build\bin` 里**一次只躺着一个架构的产物**，跳过编译不可能出两个包
- 一份 `frpc.exe` **只对应一个架构**

脚本会直接抛出带解释的错误，不会让你半路踩坑。

### 常用组合

```powershell
# 正常发版（最常用）
powershell -File tools\package.ps1 -Version 1.0.1

# 只重打 arm64（比如刚手工换了 frpc.exe）
powershell -File tools\package.ps1 -Version 1.0.1 -SkipBuild -Arch arm64 -RefreshFrpc

# 只出 x64 调试
powershell -File tools\package.ps1 -Version 1.0.1 -Arch amd64

# 用别处的 frpc.exe
powershell -File tools\package.ps1 -Version 1.0.1 -Arch amd64 -FrpcPath D:\frp\frpc.exe
```

## 五、往包里加东西（`dist-staging/` 机制）

**打包内容 = `dist-staging/` 目录里的全部文件。**

所以想加东西（额外的说明文档、配置示例、免安装脚本……）
**直接把文件丢进 `dist-staging/` 就行**，脚本不会删它
（只清理过期的 `*.exe`）。

```
cikpier/dist-staging/
├── 使用说明.md          ← 用户手册（仓库里维护的源文件）
├── LICENSE
├── CikPier.exe         ← 打包时自动拷进来（源在 app/build/bin/）
└── frpc.exe            ← 打包时自动拷进来（源在 frp-bins/）
```

> ⚠ **`CikPier.exe` 和 `frpc.exe` 不要手工放进 `dist-staging/` 然后提交。**
> 它们是构建产物，每次打包都会被覆盖；手工放的版本容易过期。
>
> ⚠ **绝对不要**把 `frpc.toml`、`frpc-store.json`、`gui-settings.json`、
> `gui-debug.log` 放进 `dist-staging/` —— 里面有你的令牌和代理列表。
> 见 §九 的检查清单。

### 用户手册的同步

用户手册的**源文件**就是 `dist-staging/使用说明.md`，它同时是：

- 仓库里唯一的手册正文
- 打进包里的那个文件

所以**改完手册必须重新打包**，否则包里还是旧的。

## 六、为什么必须出两个架构的包

x64 的程序在 Windows 11 ARM64 上**能靠模拟层启动**，看起来一切正常，
但有一类**至今仍未修复**的问题：

> WebView2 在"ARM64 系统上运行 x64 目标程序"这个组合下，
> 发送较大的消息时会**死锁**，最终整个程序崩溃。
> [MicrosoftEdge/WebView2Feedback#4589](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4589)，
> 2024-05 提交，**状态仍是 open**。

而本程序的**日志页会一次性把几百条日志传给界面** —— 正好属于"较大消息"，
有踩中的风险。再加上模拟层本身有性能损失。

所以 ARM 用户必须用原生 arm64 包。这条路是通的：

- `wails build -platform windows/arm64` 能编过 —— 实测产物 PE 头是 `machine=0xAA64`
- 依赖的库（托盘 `fyne.io/systray`、注册表 `x/sys/windows`、
  WebView2 加载器 `go-webview2`）**都是纯 Go，没有 cgo**，交叉编译没有障碍
- frp 官方**就提供** `frp_0.71.0_windows_arm64.zip`，所以 `frpc.exe` 也是原生 arm64
- WebView2 Runtime 在 Windows 11 ARM64 上是自带的（Edge 就是 ARM64 原生版）

> ⚠ **诚实说明**：目前验证到的是「能编译出正确的 ARM64 PE 文件、
> 两个 exe 架构一致、图标正确嵌入」。
> **没有在真实 ARM64 设备上跑过**（手上没有设备）。
> 首次发给 ARM 用户前，建议先在一台 ARM 机器或 ARM 虚拟机上确认一遍。

## 七、换 frp 版本

**只需要替换 `frpc.exe`（和 `frps.exe`）一个文件** ——
本程序不导入 frp 的 Go 模块，也不依赖它的命令行参数。

### 步骤

1. 从 https://github.com/fatedier/frp/releases 下载对应平台和架构的 zip
2. 解压，把 `frpc.exe` / `frps.exe` 覆盖到 `frp-bins/<平台-架构>/`
3. 更新 `app/about.go` 里的 `frpFallback`（**只影响 `frpc -v` 执行失败时的兜底显示**）
4. 重新打包：

```powershell
cd cikpier
powershell -File tools\package.ps1 -Version 1.0.1 -RefreshFrpc
```

> `-RefreshFrpc` 强制重新拷一份进包。不加的话，如果 `dist-staging/` 里
> 已有一份**同架构**的 `frpc.exe`，脚本会沿用旧的。

> 💡 **关于页显示的 frp 版本是真的执行 `frpc.exe -v` 问出来的**，
> 不是写死的。所以只要换了文件，界面上的版本号自动就对了
> （`frpFallback` 只在执行失败时才用）。

## 八、手动打包（脚本坏了 / 想完全自己控制时）

```powershell
# 0. 退出正在运行的 CikPier，避免文件占用
cd D:\Tools\frp_0.71.0\cikpier

# 1. 编译 x64
cd app
wails build -clean -skipbindings -platform windows/amd64 -o CikPier.exe
cd ..

# 2. 收集
Copy-Item app\build\bin\CikPier.exe dist-staging\ -Force
Copy-Item ..\frp-bins\win-amd64\frpc.exe dist-staging\ -Force

# 3. 自检（务必做）
#    读 PE 头确认两个 exe 都是 0x8664
$b=[IO.File]::ReadAllBytes('dist-staging\CikPier.exe'); $pe=[BitConverter]::ToInt32($b,0x3C); '{0:X}' -f [BitConverter]::ToUInt16($b,$pe+4)
$b=[IO.File]::ReadAllBytes('dist-staging\frpc.exe');    $pe=[BitConverter]::ToInt32($b,0x3C); '{0:X}' -f [BitConverter]::ToUInt16($b,$pe+4)

# 4. 打 zip
Compress-Archive -Path 'dist-staging\*' -DestinationPath '..\release\CikPier-v1.0.1-amd64.zip' -Force
```

arm64 同理，把 `amd64` 换成 `arm64`、`frp-bins\win-amd64` 换成 `frp-bins\win-arm64`。

> ⚠ 手动打包**丢掉了脚本的全部自检**（架构校验、必需文件检查、版本号交叉检查、
> 旧产物清理）。只在前两者都确认过的情况下用。

## 九、⚠ 发布前检查清单

**每一项都实际打开看一眼，不要只凭记忆。**

### 安全

- [ ] 包里**没有 `frpc.toml`** —— 里面有你的 `auth.token`，**绝不能发出去**
- [ ] 包里**没有 `frpc-store.json`** —— 那是你自己的代理列表
- [ ] 包里没有 `gui-settings.json` / `gui-debug.log` / `frpc.log` 等运行时文件
- [ ] 用 `Compress-Archive` 或资源管理器打开 zip **逐项确认上面四条**

### 正确性

- [ ] `-Version` 和 `app/about.go` 的 `appVersion` **一致**（脚本会警告）
- [ ] `使用说明.md` 是**最新版**（改过手册就要重新打包）
- [ ] 两个 exe 是**同一架构**（脚本已自动校验）
- [ ] 包名和内容对得上（`-amd64.zip` 里就是 amd64）

### 实机

- [ ] 解压到**一个干净的空目录**（不要解压到 `Program Files`，会要管理员权限）
- [ ] 双击能起来，没有一闪而过
- [ ] 首次配置向导能走完
- [ ] 走完之后顶栏能变成 🟢（需要真有一个服务端可连）
- [ ] 托盘图标在，右键菜单能开
- [ ] 关于页显示的版本、架构、frp 版本都对

### 收尾

- [ ] `release/` 里**没有**该版本的旧命名 zip（脚本会自动删）
- [ ] 发出去的包名和实际文件对得上

## 十一、打包报错怎么办

### `unlinkat ...: Access is denied.`

`app/build/bin/` 里有进程在跑。**九成是上次 `wails dev` 拉起的 `frpc.exe`。**

`tools/package.ps1` 会自动清理（用 `Get-CimInstance Win32_Process` 找
`ExecutablePath` 落在 `app\build\bin\` 下的进程然后 `Stop-Process`）。
手动 `wails build` 时要自己先退出程序和托盘的 frpc。

### `主程序架构是 arm64，和要求的 amd64 不一致`

`app/build/bin/CikPier.exe` 是上一次 arm64 构建留下的。

- 正常用 `package.ps1`（不要 `-SkipBuild`）会自动重新编译
- 用了 `-SkipBuild` 就会撞上这个 —— 换成 `-Arch arm64`，或者去掉 `-SkipBuild`

### `frpc.exe 架构是 amd64，和主程序（arm64）不一致`

`dist-staging\frpc.exe` 是别的架构留下的。

```powershell
powershell -File tools\package.ps1 -Version 1.0.1 -Arch arm64 -RefreshFrpc
```

### `找不到 arm64 版的 frpc.exe`

脚本会尝试从 GitHub Releases 下载
`frp_<版本>_windows_arm64.zip`。下载失败（网络）时：

```powershell
# 手动下载后放到 frp-bins\win-arm64\frpc.exe，或者
-FrpcPath D:\下载目录\frpc.exe -Arch arm64
```

### `包里缺少必需文件：使用说明.md`

`dist-staging/使用说明.md` 被删了。从 git 或备份恢复。
**不要**为了让脚本通过就随便建个空文件。

### `包名写的是 v1.0.1，但 about.go 里是 v1.0.0`

只是**警告**，不会中断。但界面里显示的版本会和你发的包名不一致 —— 改掉：

```go
// app/about.go
appVersion = "1.0.1"
```

### 关于 `dist-staging\` 里最后留下的是哪个架构

默认 `both` 时，**最后处理的是 arm64**，所以跑完
`dist-staging\CikPier.exe` 和 `frpc.exe` 都是 arm64 的。

**这不影响产物** —— 两个 zip 在各自那一步就打好了。
但**别拿 `dist-staging/` 直接发人**，要用 `release/` 里的 zip。

## 十二、版本号怎么定

以 `app/about.go` 的 `appVersion` 为**唯一来源**。建议语义化：

| 改动性质 | 版本 |
|---|---|
| 修 bug、改文案 | `+0.0.1` |
| 加功能、加页面 | `+0.1.0` |
| 不兼容改动（配置格式、目录结构） | `+1.0.0` |

改的时候**两处一起改**：

1. `app/about.go` 的 `appVersion`
2. 打包时的 `-Version`

（`wails.json` 的 `info.productVersion` 是给 exe 文件属性用的，也顺手同步。）
